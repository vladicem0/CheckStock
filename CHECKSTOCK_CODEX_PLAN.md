# CHECKSTOCK — план реализации для Codex

**Назначение:** готовое техническое задание и поэтапный план реализации тестового проекта «Где сейчас товар?».  
**Первоисточник:** PDF «CHECKSTOCK / ТЕСТОВОЕ ЗАДАНИЕ ДЛЯ РАЗРАБОТЧИКА» (1 стр.).  
**Контекст, но НЕ объём тестового:** «Ракета / Веб-система снабжения» (5 стр.).  
**Ожидаемый результат:** работающий, воспроизводимый веб-прототип на Python + FastAPI + PostgreSQL, репозиторий с README, тестами и тестовыми данными, сценарий для голосового видео 3–5 минут.  
**Ограничение времени:** работодатель ориентирует на 1 рабочий день; сдача по 17.11.2026 включительно.

## 3. Доменные решения для неоднозначностей

**Это проектные договорённости, а не цитаты из PDF.** Обязательно отрази их в README / DECISIONS:

1. Один магазин, два склада ФФ. Один артикул может находиться в нескольких ФФ. Многомагазинность не реализуем, но не используем глобальное складывание запасов для списания.
2. Для тестового достаточно **полных** отгрузок/приёмок одной операции с одним SKU: частичная приёмка, возвраты клиентов, брак, пересортица и корректировки не входят в scope.
3. Удаление ФФ — **архивация (`archived_at`)**. Склад с товарами не исчезает из отчётов и истории. Архивный склад явно помечается; новые приходы, резервы и входящие перемещения запрещены. Разрешено завершить уже начатые операции, включая старые входящие, а также оформить исходящее перемещение с архивного склада на активный, чтобы вывести остатки. Для новых отгрузок FBO с архивного склада — отказ; для уже зарезервированного FBS — разрешить завершение/отмену.
4. Архивный ФФ может иметь `available = on_hand - reserved`, но это **арифметический доступный остаток, не право создавать новый резерв**. UI явно обозначает, что склад архивирован и новые операции блокируются.
5. FBS после отправки становится `shipped` («в пути к клиенту»). Подтверждение доставки можно сделать как низкоприоритетное расширение, если остаётся время; иначе транзит FBS сохраняется до завершения учёта за рамками прототипа, и это документируется.
6. FBO создаётся сразу как фактическая отправка `in_transit`; отдельный черновик FBO не обязателен. Приёмка на маркетплейсе завершает транзит и фиксируется в истории; остаток ФФ от этого не увеличивается.
7. Перемещение между ФФ проходит `draft -> in_transit -> received`: создание заявки не меняет остаток, явная отправка списывает у источника, приёмка зачисляет получателю.
8. Все количества — **штучные положительные целые числа**; отрицательные операции и дроби запрещены.
9. Новые операции на одной записи остатков сериализуются транзакциями и блокировкой строки БД. Не полагаться на состояние frontend и проверку «сначала GET, потом POST».
10. У каждой операции постоянный ID. Повторное подтверждение уже выполненного перехода возвращает текущее состояние и не создаёт нового складского события.
11. Стабильные ссылки на склады через ID; в журнале событий полезно также сохранять имя ФФ на момент операции: переименование не должно делать историю непонятной.
12. Допускается отсутствие полноценной аутентификации: это локальный тестовый прототип, а не production-сервис. Не следует при этом утверждать, что система безопасна для публичного доступа.

## 4. Модель данных и инварианты

Минимальные сущности:

1. `products`: `id`, `sku` (UNIQUE), `name`.
2. `warehouses`: `id`, `name`, `archived_at NULLABLE`, `created_at`; имя можно менять, ID постоянен.
3. `stock_balances`: `product_id`, `warehouse_id`, `on_hand` (physical), `reserved_fbs`; уникальный составной ключ по SKU/ФФ.
4. `operations`: `id UUID`, `kind` (receipt, transfer, fbs, fbo), `status`, `product_id`, `qty`, `source_warehouse_id`, `destination_warehouse_id`, `idempotency_key`, `request_fingerprint`, `created_at`, `updated_at` и необходимые ссылки на внешнюю сторону (`customer`, `marketplace` как логическое назначение).
5. `stock_events`: append-only-журнал: `id`, `operation_id`, `event_type`, `product_id`, `qty`, `from_warehouse_id`, `to_warehouse_id`, момент времени, человекочитаемые снимки названий и/или deltas для аудита. История не удаляется.

Не обязательно делать таблицы `transit_balances`: для MVP **товар в пути надёжнее вычислять из операций и их статусов**:

- `transit_ff` = SUM(qty) по transfer с `status=in_transit`;
- `transit_fbo` = SUM(qty) по fbo с `status=in_transit`;
- `transit_fbs` = SUM(qty) по fbs с `status=shipped`.

Если добавляется статус `delivered`, соответствующая операция перестаёт входить в `transit_fbs`. Приёмки FBO учитываются в истории как принятые маркетплейсом, но не прибавляются обратно к запасам ФФ.

**Инварианты в БД и сервисах:**

- `on_hand >= 0`;
- `reserved_fbs >= 0`;
- `reserved_fbs <= on_hand`;
- `available = on_hand - reserved_fbs`;
- `qty > 0`;
- один SKU+ФФ — одна строка остатков;
- отгрузка/резерв выбирают и блокируют баланс **конкретного** ФФ;
- факт отправки меняет одновременно источник и состояние операции в одной транзакции;
- факт приёмки меняет одновременно транзитное состояние операции и целевой остаток в одной транзакции;
- у одного перехода операции не может быть двух одинаковых событий;
- `warehouse_id`/`product_id` в истории — ссылочная целостность без каскадного удаления.

Проверь индексы и ограничения `CHECK`, `UNIQUE`, внешние ключи `RESTRICT`/`NO ACTION`. В случаях отсутствия строки stock создавай её безопасно (например, `INSERT ... ON CONFLICT DO NOTHING`), затем блокируй `SELECT ... FOR UPDATE`. Для операций, трогающих более одного баланса, соблюдай единый порядок захвата блокировок.

## 5. Жизненный цикл операций — MUST HAVE

| Действие | Баланс источника | Резерв | В пути | Баланс получателя |
| --- | --- | --- | --- | --- |
| Приход q в A | `on_hand(A) += q` | без изменений | нет | — |
| Создать transfer A -> B | без изменений | без изменений | нет | без изменений |
| Отправить transfer A -> B | `on_hand(A) -= q` | не меняется | `transit_ff += q` | без изменений |
| Принять transfer в B | без изменений | — | `transit_ff -= q` | `on_hand(B) += q` |
| Зарезервировать FBS q в A | `on_hand(A)` не меняется | `reserved(A) += q` | нет | — |
| Отменить FBS до отправки | `on_hand(A)` не меняется | `reserved(A) -= q` | нет | — |
| Отправить FBS-клиенту | `on_hand(A) -= q` | `reserved(A) -= q` | `transit_fbs += q` | клиент вне остатков ФФ |
| Отправить FBO с A | `on_hand(A) -= q` | без изменений | `transit_fbo += q` | маркетплейс вне остатков ФФ |
| Принять FBO на маркетплейсе | без изменений | без изменений | `transit_fbo -= q` | отразить приёмку в истории, не на ФФ |

В FBS и FBO отправка возможна только при нужном доступном остатке / собственном действующем резерве; зарезервированный чужими FBS-заказами товар нельзя отправить как FBO или transfer. Проверка для перемещения/отправки: **`available_here >= qty`**, не `sum(all_warehouses) >= qty`.

Переходы статусов должны проверяться в сервисах. Примеры:

- transfer: `draft -> in_transit -> received` (нельзя получить ещё не отправленное);
- FBS: `reserved -> shipped` **или** `reserved -> cancelled` (отменённое нельзя отправить);
- FBO: `in_transit -> received` (нельзя принять дважды);
- receipt: `completed` сразу.

Реализация должна различать **повтор той же команды** и **недопустимый иной переход**:
- второй `receive` уже принятой поставки = HTTP 200 с тем же результатом, без дополнительных событий;
- попытка `ship` отменённого FBS = HTTP 409;
- повтор того же `POST create` с тем же `idempotency_key` и идентичным телом = прежний `operation_id`, никакого повторного прихода/резерва/списания;
- тот же `idempotency_key` с изменёнными данными = HTTP 409.

`request_fingerprint` должен быть детерминированным для нормализованного payload, а ограничения UNIQUE и переходы защищены транзакциями.

## 6. HTTP API и интерфейс

Точные имена роутов можно подстроить под архитектуру, но функциональные возможности обязательны.

**API минимум:**
- `GET /api/stocks` — все SKU × все ФФ, физический/резерв/доступный, флаг архива, суммы и 3 категории транзита; учитывать нулевые ячейки;
- `GET /api/warehouses`, `POST /api/warehouses`, `PATCH /api/warehouses/{id}`, `DELETE /api/warehouses/{id}` — archive, not hard delete;
- `POST /api/receipts` — приход на ФФ;
- `POST /api/transfers`, `POST /api/transfers/{id}/dispatch`, `POST /api/transfers/{id}/receive`;
- `POST /api/fbs/reservations`, `POST /api/fbs/{id}/ship`, `POST /api/fbs/{id}/cancel`;
- `POST /api/fbo/shipments`, `POST /api/fbo/{id}/receive`;
- `GET /api/operations`, `GET /api/history` — список операций, статус и журнал действий;
- `GET /docs` — OpenAPI, но не вместо пользовательского интерфейса.

**Ошибки:**
- `422` для невалидного тела запроса (отрицательное/нулевое количество, неверный формат);
- `404` для несуществующих SKU/ФФ/операций;
- `409` для нехватки на выбранном ФФ, запрещённого действия на архивном складе, недопустимого статуса или конфликта idempotency key;
- сервер возвращает понятное сообщение, включая `available_here` и `requested`, где уместно, без Python traceback.

**UI:** одна компактная понятная панель без SPA:
1. «Остатки»: матрица SKU × ФФ, `physical | reserved FBS | available`; показать нулевые значения и архивные склады.
2. «В пути»: три независимых раздела (`между ФФ`, `FBO на маркетплейс`, `FBS клиенту`) со SKU, количеством, откуда/куда, статусом.
3. «Операции»: формы прихода, создания/отправки/приёмки transfer, резервирования/отмены/отправки FBS, FBO-отправки/приёмки. Доступные действия зависят от статуса.
4. «Склады»: создать, переименовать, архивировать; после архивирования склад не исчезает из балансов/истории.
5. «История»: дата, событие, SKU, количество, источник, назначение, status/ID операции; сортировка по времени.

Показывать обновлённые цифры после мутации и inline ошибки. Не полагаться только на disabled-кнопки для идемпотентности. Для демонстрации повторного подтверждения API должен вести себя безопасно даже через Swagger/curl.

## 7. Контрольные сценарии со строгими ожидаемыми результатами

Тесты независимые: каждый запускается с чистой тестовой БД/фикстурами и одним начальным приходом.

**T01 — сидирование:** 3 SKU, 2 ФФ, 6 сочетаний SKU/ФФ (включая 0); физически 25, резерв 0, транзит 0. Повторить seed -> всё ещё 25, без новых событий прихода.

**T02 — FBS reserve и ship:** SKU-101, Север=10. Резерв 4 -> `on_hand=10, reserved=4, available=6`; отправка -> `on_hand=6, reserved=0, available=6, transit_fbs=4`. Второй `ship` не меняет числа и журнал.

**T03 — отмена FBS:** зарезервировать 3 SKU-101 на Севере и отменить -> `on_hand=10, reserved=0, available=10`; отправить отменённое нельзя; повторная отмена не меняет журнал.

**T04 — межскладской transfer:** SKU-101 Север=10, Юг=6. Создать transfer 3 -> ничего не меняется. Отправить -> Север=7, Юг=6, `transit_ff=3`. Принять -> Север=7, Юг=9, `transit_ff=0`. Второй dispatch/receive ничего не меняет. Попытка receive до dispatch = 409.

**T05 — FBO:** SKU-102 Север=5. Отгрузить 3 -> Север=2, `transit_fbo=3`. Подтвердить приёмку -> Север=2, `transit_fbo=0`, операция в статусе received, есть событие приёмки. Повторная приёмка не даёт второго эффекта.

**T06 — локальная нехватка:** SKU-103 Север=0, Юг=4. Резерв 1 на Севере -> HTTP 409, ничего не меняется. Переместить 2 с Юга на Север: после dispatch на Севере всё ещё 0, лишь после receive на Севере 2; теперь резерв возможен.

**T07 — учёт резерва при других отправках:** на Севере SKU-101 on_hand=10, reserved=8. Попытка transfer/FBO на 3 -> 409, хотя физически 10; 2 допустимо.

**T08 — архивирование ФФ с товаром:** архивировать Юг, где 10 шт. Остатки 10 не исчезают, история видна, имя/ID стабильны. Новые резерв, приход, входящее перемещение запрещены; вывести остаток transfer на активный ФФ разрешено. Повторная архивация не стирает данные.

**T09 — переименование ФФ:** переименовать Север; операции с ID продолжают работать, история показывает правильные ссылки и при необходимости снимок исходного имени.

**T10 — идемпотентный create:** два одинаковых `POST /api/receipts` с одним idempotency key -> всего один приход. Тот же ключ с иным qty -> 409.

**T11 — гонка:** два конкурентных FBS reserve по 7 единиц SKU-101 на Севере (доступно 10) -> успешно не более одного. `on_hand=10`, `reserved<=10`, отрицательного `available` не возникает. Каждый запрос использует отдельную сессию БД.

**T12 — нет частичных состояний:** вызвать ошибку в середине операции (в тестовой транзакции) и убедиться, что ни баланс, ни статус, ни журнал не изменены частично.

**T13 — история:** для всех успешных переходов есть ровно один соответствующий event; там указаны SKU, количество, источник, пункт назначения, время и ID операции. Ошибочные и повторные операции не создают дубли событий.

**T14 — финальная проверка:** открывается интерфейс, Docker Compose работает с чистого состояния; `README` даёт воспроизводимый путь к тестам и демосценарию без ручной правки Python.

## 8. Критичные технические детали

1. Объединять проверку остатка, блокировку строки, обновление баланса, смену статуса и запись истории **одной транзакцией**. Недопустимо делать check в одном запросе, update в другом без гарантий.
2. Для `receive` блокировать `operations` строку до проверки статуса; при дублирующем вызове возвращать уже подтверждённую операцию, не выполнять повторные изменения.
3. В `stock_balances` запрещены отрицательные количества; в `operations` статус должен быть согласован с типом операции.
4. Не дублировать транзит и в `stock_balances`, и в отдельной таблице без строгой необходимости — двойные источники истины усложнят тест.
5. История — append-only: обновление текущего названия склада не перезаписывает уже случившиеся события.
6. Учитывать различие **физический запас, доступный запас, FBS резерв, транзит**; не складывать резерв с физическим запасом в итогах.
7. Никаких fallback-операций с другого ФФ: можно показать подсказку «На другом ФФ есть X шт.», но не перемещать и не резервировать автоматически.
8. При нулевых остатках UI обязан показывать товар и склад (CROSS JOIN товаров и ФФ / создание 0-балансов).
9. Использовать UTC timestamps (`timestamptz`), серверные проверки и реальные уникальные ограничения, а не только клиентские блокировки.
10. Отделять экземпляр демобазы от тестового; опасные очистки применять только к тестовой БД.
11. Не делать бизнес-логику в Jinja2 или JavaScript. Все изменения проходят через FastAPI и сервисы.
12. Тестовые данные не должны появляться в production-пути без явного запуска demo seed; README должен объяснять переключатель/команду.

## 9. Пошаговый порядок реализации для Codex

- Критерий готовности: нет неясности, в какой момент конкретная операция меняет `on_hand`, `reserved` и `transit`.

### Этап B — инфраструктура и начальные данные (P0)

- Критерий готовности: чистая база, 25 шт., повторный seed не меняет количество, Postgres перезапускается с сохранением данных.

### Этап C — сервисы и транзакции (P0, важнейший)

- Сначала тесты T01–T13, особенно shortage/duplicate/concurrent.
- Критерий готовности: все операции проходят через единый сервисный слой; нет 500 на ожидаемые доменные ошибки.

### Этап D — HTTP API (P0)
- Реализовать роуты по разделу 6, Pydantic-схемы, корректные 404/409/422 и OpenAPI.

### Этап E — минимальный веб-интерфейс (P0)

- Критерий готовности: незнакомый разработчик запускает и проверяет проект по README.

### Только если осталось время (P1)
