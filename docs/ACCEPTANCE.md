# Приёмка CheckStock

Источник: CHECKSTOCK_CODEX_PLAN.md целиком; решения: DECISIONS.md. Это критерии будущей проверки, а не отчёт о пройденных тестах. Каждый сценарий независим: отдельная чистая тестовая схема PostgreSQL и один demo seed. Тестовая очистка не касается рабочей схемы public.

## Контрольные сценарии

Начальный набор: SKU-101 «Органайзер» Север=10, Юг=6; SKU-102 «Контейнер» Север=5, Юг=0; SKU-103 «Корзина» Север=0, Юг=4. Всего 25, Север=15, Юг=10. Положительные количества поступают через четыре операции прихода; нулевые ячейки не требуют фиктивных приходов.

| Код | Действия и точный ожидаемый результат |
|---|---|
| T01 | После seed: 3 SKU, 2 ФФ, 6 ячеек, physical=25, reserved=0, каждый транзит=0. Повтор seed: по-прежнему 25, число операций и событий прихода прежнее. |
| T02 | SKU-101 Север: reserve 4 → on_hand=10, reserved=4, available=6; ship → on_hand=6, reserved=0, available=6, transit_fbs=4. Повтор ship возвращает прежний ID/текущее состояние, числа и журнал неизменны. |
| T03 | SKU-101 Север: reserve 3, cancel → on_hand=10, reserved=0, available=10. ship отменённого → 409. Повтор cancel без нового события. |
| T04 | SKU-101 Север→Юг, q=3: create draft → Север=10, Юг=6, transit_ff=0, одно событие transfer_created со статусом draft; одинаковый повтор create возвращает тот же ID без нового события. receive до dispatch → 409. dispatch → Север=7, Юг=6, transit_ff=3, добавлено transfer_dispatched; receive → Север=7, Юг=9, transit_ff=0, добавлено transfer_received. Всего у этой операции три события. Повтор dispatch как в пути, так и после received, и повтор receive не меняют числа/журнал. |
| T05 | SKU-102 Север, FBO q=3: ship → on_hand=2, transit_fbo=3; receive → on_hand=2, transit_fbo=0, status=received, одно событие приёмки. Повтор receive без эффекта. |
| T06 | SKU-103 Север=0, Юг=4: reserve 1 на Севере → 409 с available_here=0, requested=1, все балансы/события неизменны. transfer 2 Юг→Север: после dispatch Север=0, Юг=2, transit_ff=2; после receive Север=2, Юг=2, transit_ff=0. reserve 1 на Севере теперь успешен. |
| T07 | SKU-101 Север: reserve 8 → on_hand=10, reserved=8, available=2. transfer dispatch q=3 и FBO ship q=3 → 409. Каждая отправка q=2 допустима в независимом варианте сценария; после неё on_hand=8, reserved=8, available=0. Создание draft transfer само запас не проверяет и не меняет. |
| T08 | Архивировать Юг с physical=10: остатки и история остаются видимы, ID/имя сохранены; повтор архивации ничего не удаляет. Новые приход, FBS reserve, FBO ship, transfer с получателем Юг → 409. Новый исходящий transfer Юг→активный Север разрешён. Старые входящие transfer и ранее созданные FBS можно завершить; ранее зарезервированный FBS можно отменить. |
| T09 | Переименовать Север: ID неизменен, операции по этому ID работают; события прошлого сохраняют снимки прежнего имени, ссылки остаются действительными, новые события получают актуальные имена. |
| T10 | Два одинаковых POST receipts с одним idempotency_key → один ID, один приход и событие. Тот же ключ с иным qty → 409, без эффекта. Повторы create проверяются до отказа по текущему архивному состоянию. |
| T11 | Два конкурентных reserve по 7 SKU-101 на Севере через отдельные сессии/транзакции: ровно один успешный и один отказ 409 при нормальном завершении обоих запросов; on_hand=10, reserved=7, available=3, один резервный event. ## Дополнительные обязательные проверки границ

- Количество 0, отрицательное, дробное, bool, строка; неверные UUID/поля → 422. Неизвестные товар, склад, операция → 404.
- БД отклоняет отрицательные on_hand/reserved, reserved>on_hand, qty<=0, дубли SKU/баланса/ключа/события, несогласованные kind/status и форму источника/назначения.
- FBS ship после cancel и cancel после ship → 409. Перемещение между одним и тем же ФФ → 422 до срабатывания ограничения БД, без изменения остатков, операций и событий.
- Независимые одноимённые товары/склады не должны использоваться для подмены стабильных ID; seed после переименования не создаёт повторный набор.
- Совпадающий ключ с другим типом операции или другим назначением → 409; конкурентные одинаковые create дают один ID и один складской эффект.
- Повторные конкурентные dispatch/receive/ship не удваивают движения и события; блокировки отсутствующего баланса безопасно создают одну запись.
- Источник transfer/FBO расходует available конкретного ФФ; нет автоматического выбора другого склада. Резерв не прибавляется к физическому итогу.
- UI показывает свежие числа после мутаций, понятные inline ошибки, статусы, архивные пометки, нули и все три транзита; зависимости локальные.
- В репозитории нет .env с паролями, venv, кэшей, временных логов и незавершённых заглушек. README честно описывает отсутствие аутентификации и ручное подтверждение FBS-доставки без интеграции с перевозчиком; DEMO_SCRIPT не выдаётся за записанное видео.

## Дополнение: подтверждение доставки FBS

По отдельному запросу после этапа F реализуется опция P1 плана. На исходных данных зарезервировать и отправить 4 SKU-101 с Севера: Север=6/0/6, физически всего=21, FBS в пути=4. Подтвердить доставку: статус delivered, FBS в пути=0, все складские остатки и чужие резервы неизменны, одно новое событие fbs_delivered. У операции три события: резерв, отправка, доставка.

Повтор deliver, повтор прежнего ship и идентичный reserve-create возвращают текущую операцию без изменений строк. Доставка из reserved/cancelled и операция другого вида → 409, неизвестный ID → 404, неверный UUID → 422. После архивации/переименования источника доставка разрешена; старые снимки имён неизменны. Ошибка записи события откатывает статус и историю. Одновременные подтверждения создают одно событие.

Миграция существующей схемы сохраняет все данные, delivered разрешён только для FBS. Downgrade при доставленных операциях отказывается без потери данных. UI показывает кнопку только у shipped FBS, после подтверждения — «Доставлено», пустой соответствующий транзит и новое событие; повтор после сбоя безопасен.

## Проверка этапа A

Контракт и DECISIONS сверены по изменениям количества, переходам, архивации, идемпотентности и изоляции тестов. Противоречий, мешающих началу этапа B, не выявлено. Детерминированные идентификаторы seed должны быть реализованы так, чтобы повтор после переименования возвращал те же склады. Повтор dispatch после received — повтор выполненной команды по событию, а не недопустимый переход назад.
