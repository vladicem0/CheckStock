# CheckStock

Локальный прототип складского учёта. Русскоязычная панель показывает остатки по SKU и ФФ, резервы и три вида транзита; позволяет оформлять приходы, перемещения, FBS/FBO, управлять складами и просматривать историю. Все действия проходят через HTTP API и транзакционные сервисы PostgreSQL. Интерактивная документация Swagger также доступна локально.

## Запуск

Нужны Git, Docker с Linux-контейнерами и Docker Compose v2+:

- **Windows:** запустите Docker Desktop и используйте PowerShell.
- **macOS:** запустите Docker Desktop и используйте Terminal (zsh или bash).
- **Linux:** запустите Docker Engine с плагином Compose и используйте bash или другую POSIX-совместимую оболочку.

Варианты установки описаны в [документации Docker](https://docs.docker.com/compose/install/). Python и PostgreSQL на хосте для приложения не требуются. Первой сборке нужен доступ к образам и Python-зависимостям.

Команды `git` и `docker compose` ниже одинаковы для всех трёх ОС. Различия в копировании файлов, HTTP-проверке и переменных окружения показаны отдельными блоками. Если не указано иное, выполняйте команды из корня репозитория.

Клонируйте репозиторий и перейдите в его каталог:

```text
git clone https://github.com/vladicem0/CheckStock.git
cd CheckStock
```

Проверьте Docker:

```text
docker version
docker compose version
```

В выводе `docker version` должны присутствовать Client и Server. Дальнейшие шаги зависят от того, есть ли уже база проекта.

Перед первым запуском проверьте, нет ли БД от предыдущего запуска проекта:

```text
docker volume ls --filter 'name=^checkstock_postgres_data$' --format '{{.Name}}'
```

Пустой вывод означает, что стандартный том проекта ещё не создан. Если выведено `checkstock_postgres_data`, PostgreSQL уже хранит данные и ранее заданный пароль. Для работы с этой БД используйте прежний `.env` и раздел [«Повторный запуск и остановка»](#повторный-запуск-и-остановка). Для чистой проверки, в том числе если прежние настройки недоступны, перейдите к [отдельной базе](#отдельная-база-для-проверки-с-нуля). Пересборка образа и повторное клонирование репозитория не создают новый том с тем же именем.

Для новой БД подготовьте настройки из примера. Команды ниже создают файл, только если он отсутствует, и сохраняют уже существующий:

Windows / PowerShell:

```powershell
if (-not (Test-Path -LiteralPath .env)) {
    Copy-Item .env.example .env
}
```

Linux / macOS:

```sh
if [ ! -e .env ]; then
    cp .env.example .env
fi
```

До первого создания БД задайте в `.env` свой случайный `POSTGRES_PASSWORD` из ASCII-букв и цифр: пароль включается в URL подключения. При необходимости измените `APP_PORT` (по умолчанию `8000`). PostgreSQL применит этот пароль при инициализации нового тома. Сохраните `.env` для следующих запусков; файл исключён из Git и контекста сборки.

```text
docker compose config -q
docker compose up --build -d
docker compose up -d --wait
docker compose ps
```

Оба сервиса должны стать `healthy`. Приложение выполняет `alembic upgrade head`, затем запускает Uvicorn от непривилегированного пользователя. [Проверка готовности](http://localhost:8000/health) возвращает `{"status":"ok"}` после успешного запроса к PostgreSQL, а при недоступности БД — HTTP 503. HTTP доступен только на `127.0.0.1`, порт PostgreSQL наружу не опубликован. Откройте [панель CheckStock](http://localhost:8000/). Дополнительно доступны [Swagger UI](http://localhost:8000/docs) и [OpenAPI JSON](http://localhost:8000/openapi.json). Если изменён APP_PORT, используйте этот порт во всех ссылках.

Проверить готовность из терминала можно так.

Windows / PowerShell:

```powershell
Invoke-RestMethod http://localhost:8000/health
```

Linux / macOS:

```sh
curl --fail --show-error http://localhost:8000/health
```

## Демонстрационные приходы

На чистой базе товары и склады отсутствуют. Миграции не создают демонстрационные данные, приложение не загружает их автоматически. Выполните seed явно, затем повторите для проверки идемпотентности:

```text
docker compose exec -T app python -m app.seed
docker compose exec -T app python -m app.seed
```

| SKU | Название | Север | Юг |
|---|---|---:|---:|
| SKU-101 | Органайзер | 10 | 6 |
| SKU-102 | Контейнер | 5 | 0 |
| SKU-103 | Корзина | 0 | 4 |

Итого: три товара, два склада, шесть ячеек остатков, физически **25 шт.**, резерв и транзиты — **0**. Четыре положительных количества оформляются как операции прихода с четырьмя событиями; нули не создают фиктивных приходов. Балансы не присваиваются напрямую. Seed использует стабильные UUID и ключи идемпотентности: повтор не удваивает количество, не сбрасывает изменённые остатки и не переименовывает справочники обратно.

Проверить количества и журнал можно через PostgreSQL:

```text
docker compose exec -T db psql -U checkstock -d checkstock -c "SELECT p.sku, w.name, COALESCE(b.on_hand, 0) AS on_hand, COALESCE(b.reserved_fbs, 0) AS reserved_fbs FROM products p CROSS JOIN warehouses w LEFT JOIN stock_balances b ON b.product_id = p.id AND b.warehouse_id = w.id ORDER BY p.sku, w.name;"
docker compose exec -T db psql -U checkstock -d checkstock -c "SELECT sum(on_hand) AS physical, sum(reserved_fbs) AS reserved FROM stock_balances; SELECT count(*) AS receipts FROM operations WHERE kind = 'receipt'; SELECT count(*) AS events FROM stock_events;"
```

## Проверки

```text
docker compose exec -T app pytest -q
docker compose exec -T app alembic check
docker compose exec -T app python -m pip check
```

Проверки складского учёта используют настоящий PostgreSQL. Каждый тест БД создаёт отдельную схему `test_checkstock_<uuid>` и применяет к ней миграцию. Очистка удаляет только собственную случайную схему; рабочая `public` и демонстрационные остатки сохраняются. На уровне сервисов и HTTP проверяются перемещения, FBS/FBO, архив и переименование, локальный дефицит, повторы, откаты, конкурентные команды и согласованные отчёты. Также проверяются HTTP-коды 404/409/422, безопасные ответы при сбоях, OpenAPI, локальные ресурсы и HTML-оболочка панели. Число запросов отчётов проверяется при росте истории, а журналирование ошибок БД — на отсутствие утечки параметров.

Успешный результат: `pytest` завершает все тесты без ошибок, `alembic check` сообщает `No new upgrade operations detected.`, а `pip check` — `No broken requirements found.`

Дополнительные браузерные тесты JavaScript описаны в [tests/browser/README.md](tests/browser/README.md). Они используют настоящую страницу и Chromium, но подменяют HTTP-ответы API для воспроизводимых проверок сбоев, повторов и интерфейса. Они не изменяют рабочую БД и не заменяют PostgreSQL-тесты. В том числе проверяются сохранение ключа после перезагрузки, его генерация без `crypto.randomUUID` и предупреждение при неопределённом результате изменения склада. Для этих тестов нужен Node.js 18+; для запуска приложения через Compose он не требуется.

**Windows / PowerShell:** если `npm` или `npx` завершаются ошибкой «выполнение сценариев отключено» (`PSSecurityException` для `npm.ps1` или `npx.ps1`), разрешите запуск сценариев только в текущем сеансе:

```powershell
Set-ExecutionPolicy -Scope Process -ExecutionPolicy Bypass
```

Выполните команду в том же окне PowerShell, где будете запускать тесты; при запросе подтвердите изменение. Область `Process` действует только для текущего сеанса и его дочерних процессов, не меняя постоянные настройки пользователя или компьютера. После закрытия этого окна для нового сеанса снова применяется обычная политика. Если ограничение задано групповой политикой организации, `Process` не может его переопределить. Подробнее — в [документации Microsoft](https://learn.microsoft.com/en-us/powershell/module/microsoft.powershell.security/set-executionpolicy#example-6-set-the-execution-policy-for-the-current-powershell-session).

Можно оставить политику без изменений: во всех Windows-командах этого раздела используйте `npm.cmd` вместо `npm` и `npx.cmd` вместо `npx`, например `npm.cmd ci --ignore-scripts`, `npx.cmd playwright install chromium` и `npm.cmd test`. Эти команды запускают CMD-обёртки Node.js вместо PowerShell-сценариев. Для Linux/macOS настройка политики PowerShell не нужна.

Для браузерных тестов сначала запустите приложение, затем установите зависимости тестов. Эти команды одинаковы для всех ОС:

Подробнее — в [инструкции Playwright](https://playwright.dev/docs/browsers#install-system-dependencies). Когда приложение работает на порту 8000, запуск тестов одинаков на всех ОС:

Для стандартного порта 8000 достаточно `npm test`. Если нужно явно указать адрес приложения, выполните из того же каталога один из вариантов ниже. При изменённом `APP_PORT` замените 8000 своим портом.

## Работа в панели

После seed обновите страницу. В разделе «Остатки» видны все шесть сочетаний товара и склада, включая нули. Физический запас, резерв FBS и доступное количество показаны отдельно; резерв входит в физический запас. Ниже отображаются три независимых вида товара в пути.

В формах выберите товар, склад и положительное целое количество. Приход увеличивает запас; заявка перемещения только создаёт операцию. Кнопки «Отправить», «Принять», «Отменить» и «Подтвердить доставку» появляются в журнале согласно текущему статусу. У отправленного FBS подтверждение доставки устанавливает «Доставлено», убирает товар из транзита клиенту и добавляет событие истории; физический запас и резерв не меняются. FBS сначала резервирует товар, FBO сразу отправляет его с ФФ. Принятый FBO остаётся в истории и не возвращается в складские остатки. Ошибка нехватки показывает доступное количество на выбранном ФФ и сколько запрошено.

После успешного действия панель перечитывает остатки, операции и историю. Если действие выполнено, но обновление не удалось, нажмите «Обновить данные»: сообщение отличает этот сбой от отказа команды. При потерянном ответе форма сохраняет исходные данные и предлагает «Повторить запрос» с прежним ключом. Пока результат неизвестен, эти поля заблокированы, чтобы повтор не превратился в новую операцию. В той же вкладке восстановление работает после перезагрузки благодаря sessionStorage; если браузер запрещает это хранилище, защита повтора сохраняется только до закрытия/перезагрузки страницы. В таком случае сначала проверьте журнал операций.

Ключ операции создаётся средствами криптографического генератора браузера, включая HTTP-адреса без `crypto.randomUUID`. Если генерация недоступна, форма показывает ошибку до отправки запроса, а введённые данные остаются доступными для исправления.

Раздел «Склады» позволяет создать, переименовать или архивировать ФФ. Архивирование требует подтверждения и сохраняет остатки и историю. Архивный ФФ остаётся в матрице и доступен как источник перемещения на активный склад. Если выбранный активный ФФ стал архивным, форма требует выбрать склад явно, не подменяя его другим. Ранее начатые операции можно завершить по прежним правилам.

Если результат изменения склада неизвестен из-за потери ответа или ошибки сервера, нажмите «Обновить данные» и проверьте список перед повтором. Создание склада не использует ключ идемпотентности, а одинаковые названия разрешены: повтор может создать второй склад. Интерфейс сообщает об этой необходимости и не повторяет запрос автоматически.

История отсортирована от новых событий к старым. Время показывается в часовом поясе устройства, точное UTC-время и полный ID доступны в подсказках. Названия складов в старых событиях сохраняются после переименования. На узком экране таблицы прокручиваются по горизонтали. Все ресурсы панели локальные; JavaScript необходим для её работы.

## Работа через API и Swagger

После seed в `/docs` раскройте `GET /api/stocks`, нажмите **Try it out → Execute**. Ответ содержит товары и склады с UUID, все шесть ячеек остатков, итоги и три списка транзита. Эти UUID используйте в телах команд; примеры в схемах Swagger показывают формат полей.

| Операция | Маршруты |
|---|---|
| Остатки, операции, история | `GET /api/stocks`, `/api/operations`, `/api/history` |
| Склады | `GET/POST /api/warehouses`, `PATCH/DELETE /api/warehouses/{warehouse_id}` |
| Приход | `POST /api/receipts` |
| Перемещение | `POST /api/transfers`, затем `/api/transfers/{operation_id}/dispatch` и `/receive` |
| FBS | `POST /api/fbs/reservations`, затем `/api/fbs/{operation_id}/ship` или `/cancel`; после отправки — `/api/fbs/{operation_id}/deliver` |
| FBO | `POST /api/fbo/shipments`, затем `/api/fbo/{operation_id}/receive` |

Для создания складской операции передайте положительное целое `qty`, UUID выбранных товара/склада и непустой `idempotency_key` длиной до 200 символов. У каждой новой операции должен быть свой ключ. Для повтора используйте **тот же ключ и те же данные**: вернётся прежний ID и текущее состояние. Ключ сохраняется точно, включая пробелы по краям; менять их при повторе нельзя. Названия складов, клиентов и маркетплейсов, напротив, обрезаются по краям. Неизвестные поля запроса отклоняются. Команды возвращают HTTP 200 и для первого успешного выполнения, и для безопасного повтора.

Для сквозной проверки создайте перемещение SKU-101 Север→Юг на 3 единицы. До `dispatch` остатки 10/6, после — 7/6 и 3 в пути, после `receive` — 7/9 и 0 в пути. В истории появятся создание черновика, отправка и приёмка. Повторите оба подтверждения: количества и события останутся прежними. Аналогично FBS резерв 4 на исходных данных меняет 10/0/10 на 10/4/6, а отправка — на 6/0/6 и 4 в пути клиенту. Подтверждение FBS-доставки через `deliver` оставляет 6/0/6 и завершает этот транзит. Повтор `deliver` или прежнего `ship` возвращает `delivered` без нового списания и события; FBO приёмка завершает транзит, не возвращая товар на ФФ. Для независимого повторения исходных сценариев используйте тесты или отдельный Compose-проект: повторный seed не сбрасывает выполненные операции.

Ошибки возвращают русское поле `detail`: 422 — неверные поля/количество/UUID, 404 — неизвестный объект, 409 — дефицит, архив, неверный переход или конфликт ключа. Дефицит дополнительно содержит `available_here` и `requested`; ошибки формы — список `errors` с полем и сообщением. Диагностика драйвера, исходное тело запроса и traceback не выдаются клиенту. Недоступность БД возвращает 503, непредвиденная ошибка — 500; незавершённая транзакция откатывается.

Swagger загружает JavaScript, CSS и favicon из `/static/vendor`, внешний валидатор отключён. После сборки для работы `/docs` CDN не нужен. Версия, лицензии и контрольные суммы ресурсов приведены в [vendor-notice](docs/vendor-notice.md).

## Отдельная база для проверки с нуля

Это необязательный сценарий для независимой проверки с исходными данными. Для обычного первого запуска достаточно предыдущих разделов.

Для проверки с исходными данными используйте имя проекта, ранее не использовавшееся в этом Docker, например `checkstock_demo`, и отдельный файл `.env.demo`. Если они уже использовались, выберите новые имена и замените их во всех командах. Это сохраняет рабочую базу и данные предыдущих проверок. Повторный seed не возвращает изменённые данные в исходное состояние.

Создайте файл из примера, сохранив существующий, если он уже есть.

Windows / PowerShell:

```powershell
if (-not (Test-Path -LiteralPath .env.demo)) {
    Copy-Item .env.example .env.demo
}
```

Linux / macOS:

```sh
if [ ! -e .env.demo ]; then
    cp .env.example .env.demo
fi
```

В новом файле задайте собственный случайный `POSTGRES_PASSWORD` из ASCII-букв и цифр и оставьте стандартный `APP_PORT=8000`. Порт 8000 должен быть свободен. Если его занимает ранее запущенный стандартный CheckStock, остановите только контейнер приложения; БД и её данные сохранятся:

```text
docker stop checkstock-app-1
```

Для параллельной работы двух экземпляров задайте отдельной базе другой свободный `APP_PORT` и используйте его в ссылках и `CHECKSTOCK_BROWSER_URL`. Команды запуска ниже одинаковы для всех ОС и выполняются из корня проекта:

```text
docker compose --env-file .env.demo -p checkstock_demo config -q
docker compose --env-file .env.demo -p checkstock_demo up --build -d
docker compose --env-file .env.demo -p checkstock_demo up -d --wait
docker compose --env-file .env.demo -p checkstock_demo exec -T app python -m app.seed
docker compose --env-file .env.demo -p checkstock_demo exec -T app python -m app.seed
docker compose --env-file .env.demo -p checkstock_demo exec -T app pytest -q
docker compose --env-file .env.demo -p checkstock_demo exec -T app alembic check
docker compose --env-file .env.demo -p checkstock_demo exec -T app python -m pip check
```

Откройте [панель отдельной базы](http://localhost:8000/) и [её Swagger](http://localhost:8000/docs). После seed и до ручных операций должны быть 25 единиц, нулевые резервы и транзиты, четыре события прихода. Все дальнейшие команды для этой базы выполняйте с теми же `--env-file` и `-p`. Например, остановка с сохранением данных:

```text
docker compose --env-file .env.demo -p checkstock_demo down
```

## Повторный запуск и остановка

Команды этого раздела относятся к стандартному проекту `checkstock` с файлом `.env`. Для отдельной базы добавляйте к каждой команде `docker compose` выбранные `--env-file` и `-p`, как в разделе выше. Используйте сохранённые настройки: повторно копировать пример или менять пароль не нужно.

```text
docker compose up -d --wait
docker compose ps
```

Если обновился код приложения, пересоберите образ с прежними настройками:

```text
docker compose up --build -d
docker compose up -d --wait
```

Пароль существующей БД хранится в томе PostgreSQL. Изменение `POSTGRES_PASSWORD` в `.env` не меняет его и может привести к ошибке `password authentication failed`. Если настройки были перезаписаны, восстановите прежний пароль в `.env`. Если нужен запуск с исходными данными и новым паролем, используйте [отдельную базу](#отдельная-база-для-проверки-с-нуля), сохранив текущий том.

Для проверки сохранения данных выполните запрос суммы до и после перезапуска PostgreSQL:

```text
docker compose exec -T db psql -U checkstock -d checkstock -c "SELECT sum(on_hand) AS physical FROM stock_balances;"
docker compose restart db
docker compose up -d --wait
docker compose exec -T db psql -U checkstock -d checkstock -c "SELECT sum(on_hand) AS physical FROM stock_balances;"
```

Если после seed не выполнять складские операции, обе суммы равны 25. После отправок часть товара находится в транзите или уже принята маркетплейсом, поэтому сумма на ФФ может быть меньше; перезапуск не должен её менять. PostgreSQL хранится в именованном томе `checkstock_postgres_data`. Обычная остановка сохраняет данные:

```text
docker compose down
```

Не удаляйте рабочий том для подготовки тестов. Отдельный Compose-проект получает собственный том; порядок описан в разделе [«Отдельная база для проверки с нуля»](#отдельная-база-для-проверки-с-нуля). Команда `docker compose config -q` проверяет конфигурацию без вывода пароля.

## Стек и правила учёта

Приложение использует Python 3.12, FastAPI, SQLAlchemy 2 + psycopg и PostgreSQL 17. Схема БД управляется миграциями Alembic, которые применяются при запуске. Панель — Jinja2 и локальный JavaScript; отдельная frontend-сборка не нужна. PostgreSQL — единственный источник складских данных. Версии Python-зависимостей приложения и тестов зафиксированы в `constraints.txt` и проверяются тестами.

Каждая складская команда изменяет остаток, статус операции и историю одной транзакцией: при ошибке изменения откатываются целиком. Блокировки и ограничения PostgreSQL защищают от отрицательного остатка, избыточного резерва и двойного списания при одновременных запросах. Создание складских операций защищено ключом идемпотентности, а повторное подтверждение выполненного действия возвращает прежнюю операцию без нового движения. История сохраняется и не перезаписывается.

Доступно = физически − резерв FBS. Резерв входит в физический запас и не прибавляется к нему. Доступность проверяется на выбранном ФФ, даже если общий запас больше. Статусы и влияние на учёт:

| Вид | Статусы | Изменение количества |
|---|---|---|
| Приход | `completed` | Увеличивает физический остаток выбранного ФФ. |
| Перемещение | `draft → in_transit → received` | Черновик записывает событие без изменения запаса; отправка списывает источник; приёмка пополняет получателя. |
| FBS | `reserved → shipped → delivered` или `reserved → cancelled` | Резерв уменьшает доступное; отправка уменьшает физическое и резерв; отмена освобождает резерв; доставка завершает транзит без изменения запасов. |
| FBO | `in_transit → received` | Отправка уменьшает физический остаток; приёмка завершает транзит без возврата товара на ФФ. |

Каждый счётчик транзита — сумма `qty` по своему виду и статусу: `transfer/in_transit`, `fbo/in_transit`, `fbs/shipped`. Принятые FBO и доставленные FBS остаются в операциях и истории, но больше не входят в транзиты и не возвращаются в остатки ФФ. Доставка FBS подтверждается вручную; связи с системой перевозчика нет. В архивной ячейке доступное число остаётся арифметической разностью и не разрешает новые резервы.

Архивация сохраняет ID, запас и историю. Новые приходы, резервы, FBO и входящие перемещения запрещены; завершение старых операций и вывод остатка на активный ФФ разрешены. Переименование не изменяет снимки имён в уже записанных событиях. Матрица включает все SKU × ФФ, включая нули и архивные склады. Транзит вычисляется из статусов операций и разделён на три категории.

Матрица и транзиты внутри одного ответа `/api/stocks` читаются из согласованного снимка PostgreSQL. Отдельные запросы панели к остаткам, операциям и истории могут отражать разные моменты времени.

Подробные решения описаны в [DECISIONS](docs/DECISIONS.md), сценарии с ожидаемыми результатами — в [ACCEPTANCE](docs/ACCEPTANCE.md), фактические результаты выполненных проверок — в [VERIFICATION](docs/VERIFICATION.md).
