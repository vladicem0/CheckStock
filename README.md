# CheckStock

Локальный прототип складского учёта по контракту [CHECKSTOCK_CODEX_PLAN.md](CHECKSTOCK_CODEX_PLAN.md). Русскоязычная панель показывает остатки по SKU и ФФ, резервы и три вида транзита; позволяет оформлять приходы, перемещения, FBS/FBO, управлять складами и просматривать историю. Все действия проходят через HTTP API и транзакционные сервисы PostgreSQL. Интерактивная документация Swagger также доступна локально.

## Запуск

Нужны Docker Engine с Linux-контейнерами и Docker Compose v2+. На Windows запустите Docker Desktop и дождитесь готовности Engine. Python и PostgreSQL на хосте для приложения не требуются. Первой сборке нужен доступ к образам и Python-зависимостям.

В корне клонированного проекта проверьте Docker:

```text
docker version
docker compose version
```

В выводе `docker version` должны присутствовать Client и Server. Создайте локальный файл настроек из примера.

PowerShell:

```powershell
Copy-Item .env.example .env
```

Linux/macOS:

```sh
cp .env.example .env
```

В `.env` замените `POSTGRES_PASSWORD` своим случайным паролем из ASCII-букв и цифр: пароль включается в URL подключения. При необходимости измените `APP_PORT` (по умолчанию `8000`). `.env` исключён из Git и контекста сборки. Для уже созданного тома изменение этой переменной само по себе не меняет пароль PostgreSQL.

```text
docker compose config -q
docker compose up --build -d
docker compose up -d --wait
docker compose ps
```

Оба сервиса должны стать `healthy`. Приложение выполняет `alembic upgrade head`, затем запускает Uvicorn от непривилегированного пользователя. [Проверка готовности](http://localhost:8000/health) возвращает `{"status":"ok"}` после успешного запроса к PostgreSQL, а при недоступности БД — HTTP 503. HTTP доступен только на `127.0.0.1`, порт PostgreSQL наружу не опубликован. Откройте [панель CheckStock](http://localhost:8000/). Дополнительно доступны [Swagger UI](http://localhost:8000/docs) и [OpenAPI JSON](http://localhost:8000/openapi.json). Если изменён APP_PORT, используйте этот порт во всех ссылках.

## Демонстрационные приходы

На чистой базе товары и склады отсутствуют. Миграции не создают демонстрационные данные, приложение не загружает их автоматически. Выполните seed явно, затем повторите для проверки идемпотентности:

```text
docker compose exec -T app python -m app.seed
docker compose exec -T app python -m app.seed
```

| SKU | Название | Север | Юг |
|---|---|---:|---:|
| SKU-101 | Органайзер | 10 | 6 |
| SKU-102 | Контейнер | 5 | 0 |
| SKU-103 | Корзина | 0 | 4 |

Итого: три товара, два склада, шесть ячеек остатков, физически **25 шт.**, резерв и транзиты — **0**. Четыре положительных количества оформляются как операции прихода с четырьмя событиями; нули не создают фиктивных приходов. Балансы не присваиваются напрямую. Seed использует стабильные UUID и ключи идемпотентности: повтор не удваивает количество, не сбрасывает изменённые остатки и не переименовывает справочники обратно.

Проверить количества и журнал можно через PostgreSQL:

```text
docker compose exec -T db psql -U checkstock -d checkstock -c "SELECT p.sku, w.name, COALESCE(b.on_hand, 0) AS on_hand, COALESCE(b.reserved_fbs, 0) AS reserved_fbs FROM products p CROSS JOIN warehouses w LEFT JOIN stock_balances b ON b.product_id = p.id AND b.warehouse_id = w.id ORDER BY p.sku, w.name;"
docker compose exec -T db psql -U checkstock -d checkstock -c "SELECT sum(on_hand) AS physical, sum(reserved_fbs) AS reserved FROM stock_balances; SELECT count(*) AS receipts FROM operations WHERE kind = 'receipt'; SELECT count(*) AS events FROM stock_events;"
```

## Проверки

```text
docker compose exec -T app pytest -q
docker compose exec -T app alembic check
docker compose exec -T app python -m pip check
```

Проверки складского учёта используют настоящий PostgreSQL. Каждый тест БД создаёт отдельную схему `test_checkstock_<uuid>` и применяет к ней миграцию. Очистка удаляет только собственную случайную схему; рабочая `public` и демонстрационные остатки сохраняются. Сценарии T01–T13 проверяются на уровне сервисов и HTTP: перемещения, FBS/FBO, архив и переименование, локальный дефицит, повторы, откаты, конкурентные команды и согласованные отчёты. Проверяются реальные HTTP-коды 404/409/422, безопасные ответы при сбоях, OpenAPI, локальные ресурсы и HTML-оболочка панели. Проверки P3 включают постоянное число запросов отчётов при росте истории и журналирование ошибок БД без утечки параметров.

Дополнительные браузерные тесты JavaScript описаны в [tests/browser/README.md](tests/browser/README.md). Они используют настоящую страницу и Chromium, но подменяют HTTP-ответы API для воспроизводимых проверок сбоев, повторов и интерфейса. Они не изменяют рабочую БД и не заменяют PostgreSQL-тесты. Для них нужен Node.js; для запуска приложения через Compose он не требуется.

Проверка зависимостей выполняется в контейнере приложения: она сравнивает фактически установленные пакеты и версии с `constraints.txt`, отклоняет неполные или повторяющиеся записи и запускает `pip check`. Пакет `pip` относится к инструментам базового образа и исключён из сравнения.

Тесты контроллера независимого ревью запускаются отдельно на хосте с Python и Git; они исключены из образа приложения и не подменяют PostgreSQL-тесты:

```text
python -m unittest discover -s tests/review -v
```

Для проверки сохранения данных выполните запрос суммы до и после перезапуска PostgreSQL:

```text
docker compose exec -T db psql -U checkstock -d checkstock -c "SELECT sum(on_hand) AS physical FROM stock_balances;"
docker compose restart db
docker compose up -d --wait
docker compose exec -T db psql -U checkstock -d checkstock -c "SELECT sum(on_hand) AS physical FROM stock_balances;"
```

Если после seed не выполнять складские операции, обе суммы равны 25. После отправок часть товара находится в транзите или уже принята маркетплейсом, поэтому сумма на ФФ может быть меньше; перезапуск не должен её менять. PostgreSQL хранится в именованном томе `checkstock_postgres_data`. Обычная остановка сохраняет данные:

```text
docker compose down
```

Не удаляйте рабочий том для подготовки тестов. Для отдельной чистой проверки задайте новое имя проекта через `docker compose -p checkstock_stage_e_check ...` во всех командах и свободный `APP_PORT` в отдельном файле настроек; такой проект получит собственный том. Команда `docker compose config -q` проверяет конфигурацию без вывода пароля.

## Работа в панели

После seed обновите страницу. В разделе «Остатки» видны все шесть сочетаний товара и склада, включая нули. Физический запас, резерв FBS и доступное количество показаны отдельно; резерв входит в физический запас. Ниже отображаются три независимых вида товара в пути.

В формах выберите товар, склад и положительное целое количество. Приход увеличивает запас; заявка перемещения только создаёт операцию. Кнопки «Отправить», «Принять» и «Отменить» появляются в журнале согласно текущему статусу. FBS сначала резервирует товар, FBO сразу отправляет его с ФФ. Принятый FBO остаётся в истории и не возвращается в складские остатки. Ошибка нехватки показывает доступное количество на выбранном ФФ и сколько запрошено.

После успешного действия панель перечитывает остатки, операции и историю. Если действие выполнено, но обновление не удалось, нажмите «Обновить данные»: сообщение отличает этот сбой от отказа команды. При потерянном ответе форма сохраняет исходные данные и предлагает «Повторить запрос» с прежним ключом. Пока результат неизвестен, эти поля заблокированы, чтобы повтор не превратился в новую операцию. В той же вкладке восстановление работает после перезагрузки благодаря sessionStorage; если браузер запрещает это хранилище, защита повтора сохраняется только до закрытия/перезагрузки страницы. В таком случае сначала проверьте журнал операций.

Раздел «Склады» позволяет создать, переименовать или архивировать ФФ. Архивирование требует подтверждения и сохраняет остатки и историю. Архивный ФФ остаётся в матрице и доступен как источник перемещения на активный склад. Если выбранный активный ФФ стал архивным, форма требует выбрать склад явно, не подменяя его другим. Ранее начатые операции можно завершить по прежним правилам.

История отсортирована от новых событий к старым. Время показывается в часовом поясе устройства, точное UTC-время и полный ID доступны в подсказках. Названия складов в старых событиях сохраняются после переименования. На узком экране таблицы прокручиваются по горизонтали. Все ресурсы панели локальные; JavaScript необходим для её работы.

## Работа через API и Swagger

После seed в `/docs` раскройте `GET /api/stocks`, нажмите **Try it out → Execute**. Ответ содержит товары и склады с UUID, все шесть ячеек остатков, итоги и три списка транзита. Эти UUID используйте в телах команд; примеры в схемах Swagger показывают формат полей.

| Операция | Маршруты |
|---|---|
| Остатки, операции, история | `GET /api/stocks`, `/api/operations`, `/api/history` |
| Склады | `GET/POST /api/warehouses`, `PATCH/DELETE /api/warehouses/{warehouse_id}` |
| Приход | `POST /api/receipts` |
| Перемещение | `POST /api/transfers`, затем `/api/transfers/{operation_id}/dispatch` и `/receive` |
| FBS | `POST /api/fbs/reservations`, затем `/api/fbs/{operation_id}/ship` или `/cancel` |
| FBO | `POST /api/fbo/shipments`, затем `/api/fbo/{operation_id}/receive` |

Для создания складской операции передайте положительное целое `qty`, UUID выбранных товара/склада и непустой `idempotency_key` длиной до 200 символов. У каждой новой операции должен быть свой ключ. Для повтора используйте **тот же ключ и те же данные**: вернётся прежний ID и текущее состояние. Ключ сохраняется точно, включая пробелы по краям; менять их при повторе нельзя. Названия складов, клиентов и маркетплейсов, напротив, обрезаются по краям. Неизвестные поля запроса отклоняются. Команды возвращают HTTP 200 и для первого успешного выполнения, и для безопасного повтора.

Для сквозной проверки создайте перемещение SKU-101 Север→Юг на 3 единицы. До `dispatch` остатки 10/6, после — 7/6 и 3 в пути, после `receive` — 7/9 и 0 в пути. В истории появятся создание черновика, отправка и приёмка. Повторите оба подтверждения: количества и события останутся прежними. Аналогично FBS резерв 4 на исходных данных меняет 10/0/10 на 10/4/6, а отправка — на 6/0/6 и 4 в пути клиенту; FBO приёмка завершает транзит, не возвращая товар на ФФ. Для независимого повторения исходных сценариев используйте тесты или отдельный Compose-проект: повторный seed не сбрасывает выполненные операции.

Ошибки возвращают русское поле `detail`: 422 — неверные поля/количество/UUID, 404 — неизвестный объект, 409 — дефицит, архив, неверный переход или конфликт ключа. Дефицит дополнительно содержит `available_here` и `requested`; ошибки формы — список `errors` с полем и сообщением. Диагностика драйвера, исходное тело запроса и traceback не выдаются клиенту. Недоступность БД возвращает 503, непредвиденная ошибка — 500; незавершённая транзакция откатывается.

Swagger загружает JavaScript, CSS и favicon из `/static/vendor`, внешний валидатор отключён. После сборки для работы `/docs` CDN не нужен. Версия, лицензии и контрольные суммы ресурсов приведены в [vendor-notice](docs/vendor-notice.md).

## Архитектура и границы

Синхронный FastAPI, SQLAlchemy 2 + psycopg, PostgreSQL 17 и Alembic. Панель — Jinja2 и локальный JavaScript без frontend-сборки и SPA. PostgreSQL — единственный источник истины; `create_all()` в пути запуска не используется. Прямые зависимости объявлены в `pyproject.toml`; точные версии прямых и транзитивных пакетов приложения и тестов зафиксированы в `constraints.txt` по проверенному образу Python 3.12/Linux. Dockerfile применяет этот файл при установке. Это фиксация Python-пакетов, а не неизменности базовых Docker-образов, ОС или хешей загружаемых файлов.

Версии обновляются намеренно: измените выбранные прямые зависимости, соберите отдельный чистый образ для Python 3.12/Linux с новыми совместимыми версиями, заново зафиксируйте полный набор установленных пакетов приложения и тестов в `constraints.txt` и пересоберите образ с этими ограничениями. Перед принятием обновления выполните сравнение установленных версий, `python -m pip check` и тесты на PostgreSQL. Существующие рабочие данные для обновления зависимостей не очищаются.

- `app/config.py`, `app/db.py` — конфигурация и сессии PostgreSQL.
- `app/models.py`, `alembic/` — таблицы, индексы и миграция.
- `app/services/stock.py` — приход, локальная доступность и общие транзакционные примитивы.
- `app/services/operations.py` — жизненные циклы перемещений, FBS и FBO.
- `app/services/warehouses.py` — создание, переименование и архивация ФФ.
- `app/services/inventory.py` — полная матрица остатков, три транзита, операции и история.
- `app/seed.py` — явные демонстрационные приходы через сервис.
- `app/api/`, `app/schemas.py` — HTTP-обработчики, контракты запросов и ответов.
- `app/main.py` — API, оболочка панели, безопасные ответы об ошибках, Swagger и проверка готовности БД.
- `app/templates/`, `app/static/app.js`, `app/static/app.css` — панель, формы и локальное оформление.
- `app/static/vendor/` — зафиксированные локальные ресурсы Swagger UI.
- `tests/` — проверки приложения; `tests/review/` — отдельный контроллер ревью.

Каждая складская команда объединяет проверку, изменение баланса, операцию и событие в одной транзакции вызывающего кода (`session.begin()`); сервис не выполняет отдельный commit. Уникальный ключ и отпечаток запроса защищают создание от повторов; повтор перехода определяется записанным событием и возвращает текущее состояние. Блокировки строки операции, складов в порядке ID и выбранного баланса сериализуют запись и согласуют её с архивацией. Списание не переключается на другой ФФ при локальном дефиците. Ограничения БД запрещают отрицательные остатки, резерв выше физического, неверные статусы/назначения и дубли событий. Журнал защищён от UPDATE/DELETE/TRUNCATE. Метки времени хранятся в `timestamptz`.

Доступно = физически − резерв FBS. Резерв входит в физический запас и не прибавляется к нему. Перемещение проходит `draft → in_transit → received`: черновик записывает одно событие `transfer_created`, отправка списывает источник, приёмка пополняет получателя. FBS резервирует доступное количество, затем либо освобождает резерв при отмене, либо списывает физический запас и резерв при отправке клиенту. FBO сразу отправляется в транзит; приёмка маркетплейсом завершает транзит без возврата на ФФ.

Архивация сохраняет ID, запас и историю. Новые приходы, резервы, FBO и входящие перемещения запрещены; завершение старых операций и вывод остатка на активный ФФ разрешены. Переименование не изменяет снимки имён в уже записанных событиях. Матрица включает все SKU × ФФ, включая нули и архивные склады. Транзит вычисляется из статусов операций и разделён на три категории.

Сервисы чтения делают несколько SQL-запросов. HTTP-отчёты используют новую сессию запроса и устанавливают `REPEATABLE READ` до первого SQL. Защита из P3 этапа C включена в D: составные сервисы отчётов проверяют фактическую изоляцию и обновляют устаревшие ORM-объекты из снимка; слабая изоляция считается ошибкой интеграции. Сами сервисы не открывают отдельную транзакцию и не меняют её изоляцию. Команды используют `READ COMMITTED` и блокировки.

В E включены два P3 из ревью D. Отчёты переиспользуют обновлённые справочники, поэтому число SQL-запросов не растёт с числом операций. Ошибки SQLAlchemy журналируются с классом и расположениями кадров; SQL, параметры и сообщения драйвера не записываются. Ошибки соединения/таймаута дают 503, внутренние ошибки SQLAlchemy — 500; клиент получает только общее русское сообщение.

Доменные договорённости зафиксированы в [DECISIONS](docs/DECISIONS.md), ожидаемые результаты — в [ACCEPTANCE](docs/ACCEPTANCE.md), состав и выполненные проверки этапа E — в [E_WEB_PANEL](docs/stages/E_WEB_PANEL.md).

Это локальный тестовый прототип без аутентификации. Не публикуйте его в интернете. Здесь нет интеграций с маркетплейсами, частичных приёмок, возвратов, многомагазинности или подтверждения доставки FBS. Финальная проверка сдачи и сценарий голосового видео относятся к этапу F.
